## 1부 — 합성 장면에서 (09-14 ~ 09-15)

### 1. 감축률을 성과로 봤다

**결정.** VLM 입력 비용을 줄이는 모듈이므로 "프레임을 몇 % 줄였나"를 성능 지표로 삼았다. 초기 구현에서 합성
53초 영상이 53 → 5장(90.6%)으로 줄었다.

**틀린 점.** 프레임을 1장만 남겨도 감축률은 98%다. 감축률은 많이 버리는 쪽이 항상 이긴다. 실제로 90.6% 는 블러
게이트가 **선명한 저텍스처 프레임까지 버려서** 나온 숫자였고, 게이트를 고친 뒤 6장(88.7%)으로 늘었다.

**바꾼 것.** 재야 하는 값을 "**무엇을 잃었나**"(장소 보존률)로 바꾸고, 판정은 파이프라인 밖(외부 OCR)에, 상한은
오라클(선별 없이 전 프레임 판정)로 깔았다 → #6.

### 2. 게이트를 구제보다 먼저 뒀다

**결정.** 품질이 낮은 프레임을 먼저 버리고 남은 프레임만 보정한다(비용이 싸다).

**틀린 점.** 실내 전시장 장면(평균 휘도 0.067) 7프레임이 전부 `underexposed` 로 탈락해 "SEOUL MUSEUM OF ART"가
결과에서 사라졌다. 어두운 프레임은 품질이 낮은 게 아니라 **복원이 필요한** 프레임이다.

**바꾼 것.** 값싼 구제(WB + 감마 + CLAHE)를 게이트 **앞**에 두고, 게이트의 정의를 "복원해도 못 읽는 프레임 제거"로
바꿨다. 구제 가능/불가능 경계를 설정으로 분리(`rescue_luma_below` / `unrecoverable_luma_below`).

### 3. 디노이징 판정 시점

**결정.** 원본 프레임의 노이즈 σ(Immerkær)가 임계(6.0)를 넘으면 디노이징.

**틀린 점.** 어두운 프레임은 화소값이 눌려 노이즈 진폭도 같이 눌린다. 원본 σ 1.26 이라 디노이징이 안 걸렸고, 감마로
들어올린 뒤 3.22, CLAHE 후 5.93 까지 증폭됐다.

**바꾼 것.** 판정을 **감마 후 재추정 σ**로, 강도를 σ 비례(h ≈ 2.5σ)로, 위치를 CLAHE 앞으로. 회귀 테스트
`test_enhance_denoises_boosted_noisy_frame`.

### 4. OpenCV 5.x 에서 MSER 실패

로컬 검증에서 opencv 5.0 의 MSER 이 합성 간판 영역을 검출하지 못해 textness 테스트가 깨졌다. 원인 분석 대신
`opencv-python-headless>=4.10,<5` 로 고정하고 이유를 `pyproject.toml` 주석에 남겼다. (미해결 — 5.x 로 올릴 때 다시 볼 것.)

### 5. 임베더가 바뀌면 유사도 스케일도 바뀐다

**결정.** 샷 분할 임계 0.88(pHash 기준)을 DINOv3 임베더에도 그대로.

**틀린 점.** DINOv3 의 코사인 유사도는 스케일이 전혀 다르다(다른 장면 쌍 최대: pHash 0.247 vs DINOv3 0.941). 결과는
감축률 94.3% 로 **개선처럼 보였지만** `BLUE BOTTLE COFFEE`·`OLD FERRY DONUT` 두 장면이 옆 장면에 합쳐져 장소 2곳이
사라졌다. 감축률만 봤다면 채택했을 변경이다.

**바꾼 것.** `Embedder` 프로토콜이 권장 임계를 함께 노출(perceptual 0.88/0.95, dinov3 0.97/0.97). 설정 기본값은
`None` = 임베더 권장값.

### 6. 보존률 하네스가 드러낸 결함 5개 — 첫 측정 6/8

**가설.** "과분할은 VLM 호출만 늘 뿐 장소를 잃지는 않으니 안전한 오류 방향이다."

**틀린 점.** 장소 8곳(저조도 3) 합성 장면에서 첫 보존률이 **6/8**. 하네스가 손실 원인(게이트 탈락 / 선별 제외 /
읽기 실패)을 분류하게 하자 결함이 하나씩 드러났다.

| 결함 | 증상 | 수정 |
|---|---|---|
| 전역 퍼센타일 블러 컷 | "흔들린 프레임이 항상 25% 있다"는 가정 — 벽이 단조로운 가게가 구간째 탈락 (lapvar 13.1k, 컷 14.1k) | ±3초 이웃 중앙값 기준 |
| 이웃 기준만 사용 | 수 초 이어지는 흔들림이 "이웃도 흐리니" 통과 (lapvar 9.8) | 영상 중앙값 5% 절대 하한 추가 |
| 구제가 선명도 스케일 변경 | CLAHE 가 lapvar 를 약 1.8배로 → 정상 노출 프레임이 하위권 | 구제 여부로 계층화 |
| 고정 장면 임계 | 패닝 시 같은 장소 인접 유사도 중앙값 0.809 < 임계 0.88 → 8곳이 샷 19개 | 영상별 인접 유사도 분포로 임계 역산 |
| 점수 순 예산 컷 | 잘 찍힌 장소가 슬롯 3개 독식 | k-center greedy (시각 다양성) |
| (보너스) 전체 ISP | 저조도에서 디노이징 강도 상한 → 간판 획 뭉개짐 | 보정 후 문자 점수가 떨어지면 구제본 출력 |

**결과.** 8/8(오라클 동률), 선별 16 → 12장, 장소당 프레임 2.3 → 1.5. 구제를 끄면 7/8, ISP 전체를 꺼도 8/8
(**ISP 추가 기여 0, 처리 시간 +45%** — 음의 결과로 기록).

> 이 수치들은 전부 합성 장면이다. 이 절에서 고친 결함 중 5번(다양성 예산 컷)은 실영상에서 오히려 역효과였다 → #12.

## 2부 — 실영상으로 (09-15)

### 7. 직접 찍은 영상 대신 유튜브

**처음 계획.** 직접 촬영한 영상 2–3편에 정답을 달아 검증.

**바꾼 이유.** Pind 가 받는 입력은 유튜브에 올라간 영상이다. 재압축(720p H.264 수 Mbps), 편집 컷, **편집 자막에 들어간
상호**, 제작자 색보정 — 촬영 원본에는 이 중 어느 것도 없다. 측정은 서비스 입력 분포에서 해야 한다.

**구현.** 영상은 저작권 때문에 커밋하지 않고 URL · 포맷 선택자 · 구간 · 정답 · sha256 만 매니페스트로 남긴다
(`benchmarks/youtube/`). 콘택트 시트(3초 간격)로 라벨하고, **정답은 결과를 보기 전에 커밋**한다.

### 8. 하네스가 한글을 조용히 0점 처리하고 있었다

한글 간판·자막을 넣은 스모크 영상으로 배관을 확인하다가 **측정 도구 쪽** 결함이 나왔다.

- 문자열 정규화가 `[^A-Z0-9]` 를 지웠다 → 한글 정답이 빈 문자열 → 빈 정답은 항상 "못 읽음". 문서 예시(`"블루보틀 성수"`)
  대로 썼다면 **오류 없이 전 장소가 '읽기 실패'** 로 나왔을 것이다. → NFKC → NFD 로 자모까지 풀어 비교, 라벨이 비면 실행 전 중단.
- 음절 단위 유사도는 한글 OCR 오인식에 가혹했다: `을지다방`→`올지다방` 0.75(탈락), 자모 단위 0.90(통과).

### 9. 판정자를 의심했다

같은 스모크 영상에서 tesseract(kor+eng, psm 3/6/11 합집합)는 오라클 **3/5**, 보정을 켠 `full` 1/5 · 끈 `no-enhance` 3/5.
그대로 믿었다면 "**미니 ISP 가 장소 2곳을 잃게 한다**"는 결론을 냈다.

오라클(선별 없이 전부 판정)이 낮다는 건 파이프라인이 아니라 판정자 문제라는 신호였다. 장면 문자 검출기인 EasyOCR 로
바꾸자 오라클 5/5, `full` 5/5, 구제를 끄면 저조도 1곳만 유실 — 합성 장면과 같은 구조가 재현됐다. 판정자를 교체 가능하게
하고(`--judge`) 유튜브 기본값을 EasyOCR 로 했다. 합성 장면은 기존 수치와 비교하려고 tesseract 를 유지하고, 리팩터링 후
표가 동일함을 확인했다.

### 10. 실측: 합성 8/8 → 유튜브 4/26

개발 3편(야간 걷기 · 편집 브이로그 · 주간 대조군), 26곳, 예산 16장.

| | 오라클 | full | no-enhance | no-rescue | no-dedup (≤200장) |
|---|---:|---:|---:|---:|---:|
| 장소 보존 | 19/26 | **4/26** | 3/26 | 4/26 | 13/26 |

보정·구제 on/off 는 결과를 거의 바꾸지 않았다 — 선별 단계에서 이미 장소가 빠지므로 보정이 기여할 기회가 없다.

### 11–12. 원인: 문자 점수 포화 + 점수를 안 보는 예산 컷

보고서의 손실 원인은 대부분 "선별 제외"였지만, 그것만으로는 **예산이 모자란지, 잘못 고르는지** 구분이 안 된다. 그래서
구간 안 프레임 405장을 전부 판정해 "어느 프레임에서 어느 장소가 읽히는가" 표를 만들고, 선별 전략을 OCR 재실행 없이 비교했다.

- **예산은 충분했다.** 표에서 탐욕적으로 고르면 영상당 8장 이하로 표 기준 오라클(18곳) 전부.
- **MSER textness 가 포화했다.** 실사 720p 프레임의 85–92% 에서 1.0. 정규화 상수(영역 120개, 면적 0.35)가 합성 장면
  기준인데 실사 프레임은 MSER 영역이 중앙값 1,000개 이상이다. 읽히는 프레임 판별 AUC 0.46–0.56.
- **예산 컷이 점수를 보지 않았다.** #6 에서 도입한 k-center 는 점수를 시작점에만 쓰고 시각적 다양성으로 고른다. 읽히는
  프레임이 4–7% 뿐인 실영상에서 "시각적으로 다양한 16장"은 대부분 음식·사람·풍경이었다. 합성 장면(55초에 간판 8곳)에서는
  다양성이 곧 장소였기 때문에 드러나지 않았다.

### 13–14. 대안 `text_nms` 를 고르고, 검출 입력을 바꿨다

같은 표에서 여러 대안(MSER 점수·면적·영역 수 × 시간 간격 0/10/20/30초, 검출기 박스 수·면적·최대 높이 × 간격 0/15/30초, 인식 결과의 새 문자열 등)을
비교해 **PP-OCRv4 DB 검출기 박스 수 내림차순 + 시간 간격**을 골랐다. 개발 세트 16장에 8/18(무작위 2.7).

구현하면서 두 가지를 확인했다.

- RapidOCR 은 Python 3.13 미지원 → 검출 단계만 onnxruntime + OpenCV 로 재구현, 원본과 **626/626 프레임 박스 수 일치**.
- 검출을 원본 프레임에 돌리면 합성 장면에서 어두운 간판이 박스 0개 → 저조도 3곳 중 2곳 유실(5/8). 게이트가 본 이미지(구제본)에
  검출하도록 바꿔 3/3(7/8). 이 변경은 **테스트 영상을 보기 전에** 했다.

이 시점의 자기 경고: *26곳짜리 개발 세트에서 대안 여러 개를 비교해 가장 좋은 것을 고르면 그 수치에는 선택 편향이 들어간다.*
그래서 기본값을 바꾸지 않고 사전 등록으로 넘어갔다.

## 3부 — 사전 등록 테스트 (09-15 ~ 09-16)

### 절차

1. 비교 설정(`full` vs `text-det`), 파라미터, 주 지표, **채택 규칙**(테스트 합산 `text-det` ≥ `full` + 3곳, 그리고 무작위 기댓값보다
   클 것), 테스트 후보 3편 + 예비 3편, 제외 기준을 문서로 커밋.
2. 테스트 3편이 모두 15분을 넘자, "장소가 가장 많은 구간"을 눈대중으로 고르지 않도록 **구간 선택 규칙을 스크립트로 먼저 커밋**
   (`choose_clip.py`: 전체 라벨 → 880초 창 중 장소 최대 → 동점은 이른 창).
3. 영상 전체를 콘택트 시트로 라벨. 정규화 후 4자 미만 문자열(`223`, `oas`, `ddp`)은 우연 일치 위험으로 일괄 제외.
   라벨·구간 커밋 — 이 시점까지 테스트 영상에 파이프라인·OCR 을 한 번도 돌리지 않음.
4. 등록한 명령 그대로 실행.

### 15. 결과 — 기각

| (35곳) | 익선동 | 부산 전포 | 동대문 야시장 | **합** |
|---|---:|---:|---:|---:|
| 오라클 | 13/15 | 13/16 | 2/4 | **28** |
| 무작위 16장 기댓값 | 2.2 | 1.4 | 0.4 | **3.9** |
| `full` (diverse) | 2 | 1 | 0 | **3** |
| `text-det` (text_nms) | 4 | 0 | 0 | **4** |

4 < 3 + 3 → **채택하지 않음. 기본값 `diverse` 유지.** 두 방식 모두 무작위와 구분되지 않는다. 개발 세트에서의 이득(8 vs 2.7)은
재현되지 않았다. 사전 등록이 없었다면 개발 세트 수치로 "무작위 대비 3배"를 주장했을 것이다.

### 16–17. 판정 후 탐색 — 왜 재현되지 않았나 (주장 근거로 쓰지 않음)

| | 익선동 | 부산 | 동대문 |
|---|---:|---:|---:|
| 장소 문자열이 읽히는 프레임 비율 | 15.1% | 9.0% | 2.4% |
| 박스 수 판별력 (AUC) | 0.75 | 0.71 | 0.48 |
| **박스 수 상위 16장의 읽힘 비율** | **6%** | **0%** | **0%** |

- **AUC 와 상위 K 성능은 다른 문제다.** 박스 수는 전체 순위로는 읽히는 프레임을 위에 두지만, 맨 위(박스 30–80개)는 메뉴판·상품
  진열대·간판 밀집 거리다. 장소 이름이 크게 잡힌 프레임은 박스가 몇 개뿐이다. 상위 K 만 쓰는 선택은 분포의 극단만 본다.
- **예산이 장소 수와 비슷하다.** 구간 안 13–16곳에 16장이면 장소당 1장 — 선택이 거의 완벽해야 한다(탐욕 선택으로는 16장에 28곳 모두 가능).
- **오프라인 시뮬레이션은 낙관적이었다.** 같은 규칙을 JPEG 프레임에 적용한 시뮬레이션은 6곳, 실제 파이프라인은 4곳.

## 교훈

1. **비용 지표는 반드시 손실 지표와 짝지어 잰다.** 감축률(#1), 임계 변경(#5) 둘 다 감축률만 보면 개선이었다.
2. **판정자부터 검증한다.** 오라클이 낮으면 파이프라인보다 측정 도구를 먼저 의심한다(#8, #9).
3. **합성 데이터는 결함을 찾는 데 쓰고, 성능을 주장하는 데 쓰지 않는다.** 합성에서 고친 결함이 실영상에서 역효과가 났다(#6 → #12).
4. **방법을 고른 데이터로 방법을 평가하지 않는다.** 작은 개발 세트의 최고 수치는 선택 편향을 포함한다 — 규칙을 먼저 커밋하고
   새 데이터로 한 번만 잰다(#13 → #15).
5. **순위 지표(AUC)가 선택 성능(top-K)을 보장하지 않는다**(#16).
6. **시뮬레이션 결과는 실제 코드로 다시 잰다**(#17).

### 다음 방향 후보 (미결정)

- **예산–비용 곡선.** 16장이라는 예산 자체를 재검토. 탐색 시뮬레이션상 64장이면 무작위 약 12곳 / text_nms 약 18곳(35곳 중).
